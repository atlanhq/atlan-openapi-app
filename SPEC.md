## 1. Overview

**Source System**: OpenAPI Specification (v3)
**Connector Name**: `openapi` (App Framework name: `openapi`)
**Package Path**: `packages/csa/openapi-spec-loader` in `atlanhq/marketplace-packages`
**Kotlin Source**: `samples/packages/openapi-spec-loader` in `atlanhq/atlan-java`
**Connector Style**: HTTP
**Description**: Fetches an OpenAPI v3 spec document from a URL (or file), parses it using
the Swagger Parser, and creates two entity types in Atlan: one `APISpec` (the spec itself)
and one `APIPath` per path defined in the spec. No database, no complex auth — the "API"
is simply an HTTP GET of a JSON or YAML document.

### Asset Types Extracted

| Asset Type | Atlan Entity Type | Parent Type | Count (typical) |
|------------|-------------------|-------------|-----------------|
| API Spec   | `APISpec`         | Connection  | 1 per run       |
| API Path   | `APIPath`         | APISpec     | N (one per path in the spec) |

**Auth Method**: None required for public OpenAPI specs. For private specs hosted behind
authentication, credentials are supplied via object-storage credentials (when using

`GET <spec_url>` — returns 200 with the OpenAPI JSON/YAML if reachable. The connector
should validate by checking that the response is valid JSON/YAML with an `openapi` field.

### 4.3 APIPath

- **Atlan Type**: `APIPath` (built-in Atlan type)
- **Source**: Each key in `spec['paths']` (e.g., `/pet`, `/pet/{petId}`, `/user/login`)

#### Qualified Name

- **Pattern**: `{api_spec_qualified_name}/{path_url}` (Atlan SDK's `APIPath.creator(pathUrl, specQN)` builds this)
- **Components**:

  | Segment | Source | Notes |
  |---------|--------|-------|
  | `api_spec_qualified_name` | QN of the parent `APISpec` | Built in the same task |
  | `path_url` | `paths` dict key, e.g. `/pet/{petId}` | Raw URI string from the spec |

#### Attribute Mapping

| Atlan Field | Source | Transform | Required | Guard |
|-------------|--------|-----------|----------|-------|
| `qualified_name` | built by `APIPath.creator(pathUrl, specQN)` | — | yes | — |
| `name` | `path_url` (the paths dict key) | same value as `api_path_raw_uri` | yes | — |
| `connector_name` | constant | `"api"` | yes | — |
| `connection_qualified_name` | `connection.qualified_name` | — | yes | — |
| `api_path_raw_uri` | `path_url` (the paths dict key) | — | yes | — |
| `api_path_summary` | `path_item['summary']` | — | no | `if path_item.get('summary')` |
| `api_path_available_operations` | operations present in `path_item` | list of uppercase HTTP methods found: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | no | only include methods where the operation object is non-null |
| `description` | constructed markdown table | See note below | no | only set if at least one operation present |
| `api_path_is_templated` | `path_url` | `True` if `"{"` and `"}"` both appear in the path URL, else `False` | yes | — |

**Description construction**: The Kotlin implementation builds a markdown table:
```
| Method | Summary|
|---|---|
| `GET` | <operation.summary> |
| `POST` | <operation.summary> |
...
```
One row per HTTP method present on the path. Only methods with a non-null operation object
are included. The Python implementation should replicate this format exactly.

#### Relationships

| Field | Target Type | Target QN | Condition |
|-------|-------------|-----------|-----------|
| `api_spec` | `APISpec` | `api_spec_qualified_name` | always |

#### Hashable Content

```python
{
    "name": path_url,
    "api_path_raw_uri": path_url,
    "api_path_summary": path_item.get("summary", ""),
    "api_path_available_operations": sorted(operations),
    "api_path_is_templated": "{" in path_url and "}" in path_url,
}
```

- **Notes**: The Kotlin implementation batches path saves in groups of 20 using `AssetBatch`. The App Framework connector handles batching internally via the transform/load pipeline.

## 5. Extraction Strategy

### I/O Strategy

**I/O approach**: async httpx

The spec URL is fetched with a single `GET` request using `httpx.AsyncClient`. No authentication
header is required for public specs. YAML specs must be parsed with `PyYAML` or `ruamel.yaml`
after fetching.

### Task Splitting

**Pattern**: Per-scope-item bundled (indivisible API exception)

All three indivisibility conditions are met:

- [x] **No type filter on the endpoint**: The endpoint IS the spec URL — a raw HTTP GET
  of a JSON/YAML document. There is no `?type=` or equivalent filter; the entire document
  is returned in one response.
- [x] **Single call returns multiple entity types mixed**: One `GET <spec_url>` response
  contains both the APISpec data (in `info` + root fields) and all APIPath data (in `paths`).
  They cannot be separated at the HTTP level.
- [x] **Separate per-type calls require extra expensive operation**: Splitting into two tasks
  would require downloading the same spec file twice — one download per entity type.

One `@task extract_spec(ExtractSpecInput) -> ExtractSpecOutput` downloads the spec and writes:
- `api_spec.jsonl` — exactly 1 record (the spec metadata)
- `api_path.jsonl` — N records (one per path)

```
run() orchestration:
  1. extract_spec(spec_url)     ← single @task; GET spec URL once; emits both files
  2. compute_counts             ← no parent/child counts needed (flat hierarchy)
  3. diff                       ← standard change detection (if checkpoint_dir provided)
  4. transform                  ← map ConnectorRecords to pyatlan APISpec + APIPath assets
  5. load                       ← sync output, call atlan-loader child app
```

Since each run handles exactly one spec URL (or file), there is no `resolve_scope` step.

### Pagination

None. The OpenAPI spec is a single document returned in full in one HTTP response.
For ZIP files (legacy `CLOUD` mode), the file is extracted and each contained spec file
is processed sequentially — the App Framework implementation can treat each file as a
separate run or loop within the same task.

## 9. Source API / SQL Reference

### HTTP Connectors

#### `GET <spec_url>`

- **Auth**: None (for public specs). For private specs, include auth in the URL or use
  `Authorization` header if needed.
- **Pagination**: None — single document returned in one response
- **Returns**: OpenAPI 3.x document in JSON or YAML format
- **Content-Type**: `application/json` or `application/yaml` / `text/yaml`
- **Used for**: All entity types (APISpec + APIPath)

**Example URL**: `https://petstore3.swagger.io/api/v3/openapi.json`

**Top-level fields extracted**:
```
openapi           → api_spec_type (e.g. "3.0.4")
info.title        → APISpec name
info.version      → api_spec_version
info.description  → description
info.termsOfService → api_spec_terms_of_service_url
info.contact.email → api_spec_contact_email
info.contact.name  → api_spec_contact_name
info.contact.url   → api_spec_contact_url
info.license.name  → api_spec_license_name
info.license.url   → api_spec_license_url
externalDocs.url         → api_external_docs["url"]
externalDocs.description → api_external_docs["description"]
paths             → dict of path_url → PathItem (for APIPath records)
```

**Per-path fields extracted** (from `paths` object):
```
<key>             → path_url (e.g. "/pet/{petId}")  → name + api_path_raw_uri
<value>.summary   → api_path_summary
<value>.get       → "GET" in api_path_available_operations (if non-null)
<value>.post      → "POST" in api_path_available_operations (if non-null)
<value>.put       → "PUT" in api_path_available_operations (if non-null)
<value>.patch     → "PATCH" in api_path_available_operations (if non-null)
<value>.delete    → "DELETE" in api_path_available_operations (if non-null)
<value>.get.summary, .post.summary, etc. → description (markdown table rows)
```

## 11. Edge Cases and Gotchas

### Conditional Steps (from Argo `when:` conditions)

- **Azure file move**: The `move` step only runs when `cloud_provider == azure && is_azure_artifacts == false && spec_file_id != ''`. The App Framework implementation handles file-based input differently and this Azure-specific step is not reproduced.

### Import Modes

Three import modes exist in the Argo connector:
- `URL` — HTTP fetch (primary mode for App Framework)
- `CLOUD` — object storage retrieval (S3/Azure/GCP); App Framework can implement this
  via reading a pre-downloaded file or presigned URL
- `DIRECT` — local file upload via Atlan UI; not applicable in App Framework context

### ZIP File Support

The Kotlin connector supports ZIP files containing multiple JSON/YAML specs. Each file
in the ZIP is processed sequentially. If implementing ZIP support in the App Framework,
extract the ZIP in-memory and call `extract_spec()` for each contained spec file.

### YAML Parsing

The Kotlin connector uses the Swagger Parser (`OpenAPIV3Parser`) which handles both JSON
and YAML transparently. The Python connector must detect the format from the `Content-Type`
response header or file extension and use `json.loads()` for JSON or `yaml.safe_load()`
for YAML.

### Description Markdown Format

The `description` field on `APIPath` is a markdown table constructed by the Kotlin code:
```
| Method | Summary|
|---|---|
| `GET` | Finds Pets by status |
| `POST` | Add a new pet to the store |
```
Only methods with a non-null operation object are included. The Python implementation
must produce the same format for round-trip consistency.

### Missing Fields

Many `info` sub-fields are optional (contact, license, externalDocs). The Kotlin connector
uses Kotlin's `?.` safe-call operator and defaults to empty string `""` for all missing
fields. The Python implementation should guard with `dict.get()` and only set fields when
non-empty.

### APISpec Reuse

If a spec is loaded twice (same title + connectionQN), the Kotlin connector detects a NOOP
mutation and logs "reusing existing APISpec". The App Framework diff step handles this via
change detection on the hashable content.

### Rate Limiting

Not applicable — this is a single GET request to a static document endpoint. No rate
limiting expected for public spec URLs.

### Auth Quirks

Public OpenAPI specs (like Petstore) require no authentication. Private specs may require
custom auth; the connector currently has no first-class auth credential model for the spec
URL itself — auth must be embedded in the URL or handled via object storage credentials.
